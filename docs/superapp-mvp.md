# مستند MVP سوپراپلیکیشن

> وضعیت: تصمیم‌های محصول و معماری MVP تأیید شده‌اند؛ جزئیات API و چند مورد Open Decision باید پیش از توسعه نهایی قطعی شوند.
>
> آخرین بازبینی: ۱۴۰۵/۰۹/۰۳ — 2026-11-24
>
> مخزن مرجع پیام‌رسان: [omidnami/support-hub](https://github.com/omidnami/support-hub)

## ۱. هدف این سند

این سند مرجع مشترک برای طراحی و پیاده‌سازی نسخه MVP یک سوپراپلیکیشن موبایل است که ماژول‌های زیر را دارد:

- چت پشتیبانی چندسطحی
- مدیریت فروشگاه اینترنتی، فقط‌خواندنی
- حسابداری، فقط‌خواندنی
- CRM کاملاً محلی و شخصی
- نسخه PWA آنلاین
- تم روشن، تاریک و خودکار بر اساس سیستم
- امکان شخصی‌سازی رنگ‌های اپلیکیشن توسط کاربر

این سند باید سه کار را انجام دهد:

1. تصمیم‌های تأییدشده را حفظ کند.
2. محدودیت‌ها و پیش‌نیازهای فنی را شفاف کند.
3. به توسعه‌دهنده یا مدل بعدی اجازه دهد بدون حدس‌زدن، معماری و کامپوننت‌ها را پیاده‌سازی کند.

در این سند، نام‌های «Planet»، «سرور فروشگاه» و «بک‌اند اصلی» به یک سیستم مرجع اشاره دارند: بک‌اند کسب‌وکار محصول که مسئول احراز هویت کاربر، تاریخچه پیام، تخصیص گفتگو، سطوح پشتیبانی، فروشگاه و حسابداری است.

### مراجع فقط‌خواندنی

```text
./planet        # سورس مرجع Planet؛ فقط مطالعه و استخراج قرارداد
./support-hub   # سورس مرجع Support Hub؛ فقط مطالعه و استخراج قرارداد
```

این دو پوشه در `.gitignore` قرار دارند. هیچ فایلی در آن‌ها تغییر نمی‌کند و هیچ Migration، Test یا Build داخل آن‌ها اجرا نمی‌شود. تمام توسعه سوپراپ در `apps/`، `packages/`، `features/` و `docs/` انجام می‌شود. تغییرات موردنیاز Backend در `docs/backend-change-requests.md` ثبت و به توسعه‌دهنده دیگر تحویل داده می‌شود.

## ۲. اصول حاکم

1. **Support Hub فقط لایه انتقال Real-Time است.**
   Hub مسئول ذخیره تاریخچه، مدیریت اپراتور، سطح پشتیبانی، تخصیص گفتگو یا سیاست دسترسی نیست.

2. **اپلیکیشن مستقیم به Hub متصل می‌شود.**
   اتصال WebSocket فقط در Hub وجود دارد و اپ برای ارسال و دریافت زنده پیام باید مستقیماً به Hub وصل شود.

3. **اپلیکیشن هرگز Project Token ریشه Hub را دریافت نمی‌کند.**
   اتصال اپ باید با مجوز کوتاه‌عمر و محدود انجام شود که Planet صادر می‌کند.

4. **Planet System of Record تاریخچه و داده‌های کسب‌وکار است.**
   پیام‌های ازدست‌رفته، تاریخچه، وضعیت گفتگو و اطلاعات فروشگاه و حسابداری از API Planet خوانده می‌شوند.

5. **حالت آفلاین در MVP فقط‌خواندنی است.**
   هیچ سفارش، سند حسابداری، محصول، موجودی یا پیام آفلاین ارسال نمی‌شود.

6. **سینک یک‌طرفه است.**
   داده از سرور به SQLite دستگاه می‌آید. Outbox، صف نوشتن آفلاین و حل تعارض نوشتن در MVP وجود ندارد.

7. **CRM هیچ ارتباطی با سرور ندارد.**
   داده CRM محلی، شخصی و مستقل است.

8. **دسترسی را نباید فقط با UI کنترل کرد.**
   اگر سطوح پشتیبانی باید داده‌ها را از هم جدا کنند، مجوز باید در Hub یا لایه احراز هویت اعمال شود؛ فیلتر کردن لیست در اپ کافی نیست.

9. **رنگ‌ها از طریق Design Token مدیریت می‌شوند.**
   رنگ خام داخل کامپوننت‌ها hard-code نمی‌شود.

10. **کامپوننت‌ها باید کوچک، قابل‌استفاده مجدد و مستقل از منطق کسب‌وکار باشند.**

11. **عضویت و ورود سراسری وجود ندارد.**
    هر سرویس اتصال و احراز هویت مستقل خودش را دارد؛ نشست یک سرویس به سرویس دیگر منتقل نمی‌شود.

12. **CRM بدون اتصال به هیچ سرویس قابل‌استفاده است.**
    قفل محلی CRM اختیاری و مستقل از Auth سرویس‌هاست.

13. **ناوبری اصلی سه‌دکمه‌ای است.**
    سوپرآپ، پیام‌رسان و مدیریت حساب، هرکدام محیط مستقل و رنگ اختصاصی دارند.

14. **جزئیات امنیتی MVP فعلاً Mock هستند.**
    قرارداد نهایی Auth، Ticket و مجوزها پس از تأیید، با سرویس واقعی جایگزین می‌شود.

## ۴. محدوده MVP

### ۴.۱. داخل محدوده

- اتصال و احراز هویت مستقل برای هر سرویس
- مدیریت Session جداگانه پیام‌رسان و مدیریت حساب
- دریافت Connection Ticket از Planet؛ در MVP با Mock امنیتی
- اتصال مستقیم Socket.IO به Support Hub
- دریافت و ارسال پیام متنی آنلاین
- دریافت و ارسال فایل آنلاین، در صورت آماده‌بودن مسیر رسانه Planet
- دریافت، ضبط و پخش ویس آنلاین، با توجه به محدودیت‌های کانال مقصد
- ایموجی از کیبورد سیستم
- صف گفتگوها و فیلتر بر اساس سطح، وضعیت، کانال و اپراتور
- تاریخچه پیام صفحه‌بندی‌شده
- مشاهده آفلاین تاریخچه و داده‌های مجاز
- تخصیص، ارتقا، بستن و بازکردن گفتگو، در صورت وجود API معادل در Planet
- داشبورد، لیست و جزئیات فقط‌خواندنی فروشگاه
- داشبورد، لیست، گزارش و جزئیات فقط‌خواندنی حسابداری
- CRM محلی شامل مخاطب، برچسب، یادداشت، وظیفه و تاریخچه تعامل
- تم سیستم/دستی و شخصی‌سازی رنگ برند
- PWA آنلاین با رابط مشترک و بدون کش داده‌های کسب‌وکار

### ۴.۲. خارج از محدوده

- ارسال پیام در حالت آفلاین
- ثبت یا ویرایش سفارش در حالت آفلاین
- ثبت یا ویرایش سند حسابداری در حالت آفلاین
- سینک CRM با سرور
- عضویت یا ورود سراسری
- انتقال Session بین سرویس‌ها
- همکاری چندکاربره روی CRM
- گفتگوی گروهی یا کانال
- اتصال فعال واتساپ، تلگرام، روبیکا، ایتا یا اینستاگرام
- پیام صوتی آفلاین
- تحویل تضمینی پیام وقتی اپ و Planet هر دو آفلاین باشند
- نشان دادن `delivered` نهایی به مشتری، تا زمانی که Planet تأیید نهایی دریافت کند
- ذخیره دائمی فایل در Hub
- چندپروسه‌ای Hub بدون Redis Socket.IO Adapter
- معماری Microservices
- شخصی‌سازی کامل و آزادانگار همه رنگ‌های وضعیتی سیستم

## ۶. معماری امن اتصال به Support Hub

### ۶.۱. محدودیت فعلی Hub

طبق مستندات فعلی `support-hub`:

- اتصال اپراتور با `auth: { token: PROJECT_TOKEN }` انجام می‌شود.
- Hub اپراتور فردی، سطح پشتیبانی یا مجوز کانال را نمی‌شناسد.
- همه اتصال‌های اپراتور یک پروژه در اتاق `project:{project_id}` قرار می‌گیرند.
- Project Token ریشه دسترسی پروژه است و نباید در اپ، مرورگر یا localStorage قرار بگیرد.
- Hub تنها یک پروسه و بدون Redis Socket.IO Adapter پشتیبانی می‌شود.

بنابراین API صدور Ticket به‌تنهایی کافی نیست؛ تیم توسعه Hub باید Ticket جدید را بپذیرد. این تغییر در چارچوب سوپراپلیکیشن فقط مستند و تحویل داده می‌شود.

### ۶.۲. پیش‌نیاز تغییر Hub

Hub باید علاوه بر حالت قدیمی، اتصال اپراتور با Ticket کوتاه‌عمر را بپذیرد:

```text
auth: { connection_token: "<SIGNED_TICKET>" }
```

Ticket باید توسط Hub اعتبارسنجی شود و دست‌کم این اطلاعات را داشته باشد:

| Claim | توضیح |
|---|---|
| `iss` | صادرکننده؛ Planet |
| `aud` | مخاطب؛ Support Hub |
| `sub` | شناسه اپراتور |
| `project_id` | پروژه یا فروشگاه مجاز |
| `support_level` | سطح پشتیبانی |
| `allowed_sources` | کانال‌های مجاز |
| `iat` | زمان صدور |
| `exp` | زمان انقضا |
| `jti` | شناسه یکتای Ticket برای جلوگیری از replay در صورت پیاده‌سازی denylist |

پیشنهاد عمر Ticket: چند دقیقه؛ مقدار نهایی در Open Decisions ثبت شود.

### ۶.۳. جریان صدور Ticket

```text
اپ
 ├─ اتصال مستقل به سرویس پیام‌رسان
 ├─ دریافت Service Session Token
 └─ POST /api/chat/connection-ticket
          │
          ▼
Planet
 ├─ اعتبارسنجی نشست
 ├─ بررسی عضویت اپراتور در پروژه
 ├─ بررسی سطح پشتیبانی و کانال‌های مجاز
 └─ صدور Ticket امضاشده و کوتاه‌عمر
          │
          ▼
اپ
 └─ اتصال Socket.IO به Hub با connection_token
```

اپ نباید Ticket را در SQLite یا حافظه بلندمدت ذخیره کند. Ticket در حافظه نگه داشته می‌شود و پیش از انقضا یا پس از `session_expired` از Planet تازه می‌شود.

### ۶.۴. Fallback غیرمجاز

اگر Hub امکان پذیرش Ticket را نداشته باشد:

- بازگرداندن Project Token به اپلیکیشن مجاز نیست.
- ذخیره Project Token در SecureStore یا Keychain، مشکل دسترسی و اختیارات را حل نمی‌کند.
- فیلتر کردن مجوزها فقط داخل UI، جایگزین احراز هویت سرور نیست.

در این حالت، پشتیبانی Ticket در Hub باید پیش از انتشار نسخه چندسطحی و توسط توسعه‌دهنده Hub انجام شود.

### ۶.۵. فایل‌ها و رسانه

Endpoint فعلی `GET /api/files` در Hub با Project Token محافظت می‌شود. با معماری Ticket، اپ نباید برای دریافت فایل به Project Token نیاز داشته باشد.

راه‌های مجاز:

1. Planet فایل را از Hub دریافت و از endpoint خودش به اپ تحویل دهد؛ یا
2. Hub فایل را با Connection Ticket و مجوز سطح گفتگو قابل‌دسترسی کند.

تصمیم پیشنهادی MVP: **Planet به‌عنوان میانجای رسانه** عمل کند تا کنترل دسترسی و آفلاین‌سازی فایل‌ها یکپارچه بماند.

## ۷. جریان پیام و ذخیره تاریخچه

### ۷.۱. قرارداد پیام Hub

Hub باید قرارداد هفت‌فیلدی خود را حفظ کند:

```json
{
  "user_id": "501",
  "sender": "operator",
  "text": "سلام",
  "file": null,
  "robot_id": "987654",
  "timestamp": 1794841200000,
  "source": "bale"
}
```

`message_id`، `conversation_id`، `support_level` و وضعیت تحویل جزو قرارداد هفت‌فیلدی Hub نیستند. Planet هنگام ingest، شناسه‌های ماندگار خود را می‌سازد.

### ۷.۲. ذخیره همه پیام‌ها در Planet

مستندات فعلی Hub/webhook یک محدودیت مهم دارند:

- اگر اپراتوری آنلاین باشد، پیام فقط emit می‌شود و webhook صدا زده نمی‌شود.
- بنابراین Planet با webhook فعلی، تاریخچه کامل پیام‌های آنلاین را ندارد.

برای MVP، تیم Planet باید **همه پیام‌های ورودی و خروجی** را دریافت و ذخیره کند. یکی از این مسیرها لازم است:

- Hub برای هر پیام یک رویداد `message.ingest` به Planet بفرستد.
- Planet یک Socket client دائمی روی Hub داشته باشد و همه پیام‌ها را ingest کند.
- Hub webhook را برای همه پیام‌های ورودی فعال کند، نه فقط حالت آفلاین؛ و برای پیام اپراتور مسیر جداگانه‌ای وجود داشته باشد.

ذخیره فقط در UI اپلیکیشن برای System of Record کافی نیست.

### ۷.۳. ارسال پیام آنلاین

1. کاربر پیام را در Composer می‌نویسد.
2. اپ یک `client_mutation_id` موقت تولید می‌کند.
3. پیام از Socket Hub ارسال می‌شود.
4. Hub پیام را مسیریابی می‌کند.
5. Planet پیام را با شناسه ماندگار ذخیره می‌کند.
6. اپ پیام موقت را با نسخه canonical Planet جایگزین می‌کند.
7. در صورت timeout، اپ پیام را «نامشخص» نشان می‌دهد و بدون Idempotency Key ارسال مجدد خودکار نمی‌کند.

### ۷.۴. دریافت پیام زنده

- اپ رویدادهای Hub را می‌شنود.
- هر پیام پیش از نمایش با Ticket و پروژه فعلی اعتبارسنجی می‌شود.
- پیام با `message_id` داخل SQLite ذخیره می‌شود.
- پیام تکراری با upsert حذف می‌شود.
- پیام متعلق به سطح یا کانال غیرمجاز باید در سمت سرور/Hub مسدود شود.

### ۷.۵. reconnect و دریافت backlog

ترتیب امن پیشنهادی:

1. اتصال Socket برقرار می‌شود.
2. پیام‌های زنده در یک Buffer موقت نگه داشته می‌شوند.
3. اپ Backlog را از Planet دریافت می‌کند.
4. Backlog و پیام‌های Buffer در یک تراکنش محلی merge می‌شوند.
5. تکراری‌ها بر اساس `message_id` حذف می‌شوند.
6. Cursor محلی به‌روز می‌شود.
7. UI وضعیت «همگام» را نشان می‌دهد.

این الگو از ازدست‌رفتن پیام بین لحظه اتصال Socket و دریافت Backlog جلوگیری می‌کند.

- بازگرداندن گفتگو به سطح پایین‌تر، در صورت نیاز
- بستن و بازکردن گفتگو
- نمایش اپراتور مسئول
- فیلتر «ارجاع‌شده به من» و «بدون اپراتور»

### ۸.۲. مرز مسئولیت

| موضوع | Planet | Hub | اپ |
|---|---|---|---|
| تعریف سطوح | بله | خیر | نمایش |
| عضویت اپراتور در سطح | بله | اعتبارسنجی Ticket | نمایش |
| تخصیص گفتگو | بله | خیر | درخواست/نمایش |
| ارتقای گفتگو | بله | خیر | درخواست/نمایش |
| جداسازی پیام سطح‌ها | صدور مجوز | اعمال Room/Subscription | نمایش |
| فیلتر لیست | API | خیر | UI |

اگر همه اپراتورهای یک پروژه مجاز به دیدن همه گفتگوها هستند، سطوح فقط دسته‌بندی و تخصیص‌اند.

اگر دسترسی سطح‌ها متفاوت است، تیم Hub باید Room سطح‌بندی‌شده یا Subscription مجاز بسازد. مثال:

```text
project:{project_id}:level:{support_level}
conversation:{conversation_id}
```

فهرست Conversationهای مجاز می‌تواند از Ticket، Subscription Request یا یک API مجوز Hub دریافت شود.

## ۱۲. معماری آفلاین و سینک

### ۱۲.۱. مدل کلی

MVP از الگوی زیر استفاده می‌کند:

```text
Planet API ── Pull ──► Repository ──► SQLite ──► UI
```

ویژگی‌های زیر در MVP وجود ندارند:

- Outbox
- صف ارسال تغییرات محلی
- `web_updated_at = NULL` برای pending
- Last-write-wins بین کلاینت و سرور
- Conflict Resolution برای نوشتن آفلاین

### ۱۲.۲. داده‌های محلی پیشنهادی

| Entity | محتوای اصلی |
|---|---|
| `cached_conversations` | شناسه گفتگو، مشتری، سطح، وضعیت، اپراتور، `updated_at`، `last_synced_at` |
| `cached_messages` | `server_id`، `conversation_id`، فرستنده، متن، metadata فایل، زمان، وضعیت |
| `cached_orders` | snapshot سفارش |
| `cached_products` | محصول، تنوع، موجودی |
| `cached_accounting_documents` | snapshot سند و تراکنش |
| `cached_reports` | گزارش‌های پایه |
| `sync_state` | نام مجموعه داده، cursor، `last_synced_at`، وضعیت |
| `app_settings` | تم، رنگ برند، تنظیمات نمایش |
| `crm_contacts` | مخاطب محلی |
| `crm_tags` | برچسب محلی |
| `crm_notes` | یادداشت محلی |
| `crm_tasks` | وظیفه محلی |
| `crm_interactions` | تعامل محلی |

### ۱۲.۳. ستون‌های سینک

روی داده سرور:

- `id`
- `updated_at`
- `deleted_at` یا `version`

روی داده محلی:

- `server_id`
- `synced_at`
- `last_synced_at`
- `sync_cursor`
- `cache_status`

Cursor افزایشی سرور ترجیح دارد. استفاده از `updated_at > last_sync` باید با همپوشانی زمانی، صفحه‌بندی و Idempotency انجام شود تا تغییرات هم‌زمان از دست نروند.

### ۱۲.۴. حذف داده

حذف باید با یکی از این روش‌ها منتقل شود:

- Tombstone با `deleted_at`
- Change Log
- جایگزینی کامل snapshot برای مجموعه‌های کوچک

حذف فیزیکی سمت سرور بدون Tombstone باعث می‌شود رکورد حذف‌شده در دستگاه باقی بماند.

### ۱۲.۵. رسانه آفلاین

- metadata پیام و فایل همیشه در تاریخچه محلی نگهداری می‌شود.
- خود فایل فقط وقتی دانلود می‌شود که کاربر آن را باز کند یا سیاست کش اجازه دهد.
- اگر پخش ویس آفلاین الزامی نیست، ویس آفلاین به‌صورت metadata و دکمه «نیاز به اینترنت» نمایش داده می‌شود.
- دانلود عمدی فایل باید محدودیت حجم، سیاست Retention و امکان پاک‌سازی داشته باشد.

### ۱۲.۶. خطا و Retry

- سینک ناموفق نباید داده سالم محلی را پاک کند.
- cursor فقط بعد از commit موفق محلی جلو می‌رود.
- خطای Auth باید نشست را برای تازه‌سازی Ticket علامت بزند.
- خطای شبکه با Backoff و تلاش مجدد مدیریت می‌شود.
- اتصال به اینترنت به‌تنهایی به معنای سلامت Planet یا Hub نیست.

## ۱۶. امنیت و حریم خصوصی

- ارتباط Planet فقط با HTTPS.
- ارتباط Hub فقط با WSS.
- عضویت و ورود سراسری وجود ندارد؛ هر سرویس Session مستقل خودش را دارد.
- در MVP، جزئیات Auth، Ticket و مجوزها Mock هستند و طبق قرارداد نهایی بعدی جایگزین می‌شوند.
- Project Token، Source Token و Client Key هرگز در اپ ذخیره نمی‌شوند.
- Connection Ticket در حافظه و با عمر کوتاه نگهداری می‌شود.
- Service Session Token هر سرویس در SecureStore/Keychain/Keystore نگهداری می‌شود.
- در PWA، Token ریشه Hub ممنوع است؛ Ticket فقط در حافظه نگه داشته می‌شود.
- Ticket باید محدود به پروژه، اپراتور، سطح و کانال باشد.
- ابطال Ticket یا خروج از سرویس پیام‌رسان باید فقط اتصال Hub همان سرویس را قطع کند.
- SQLite حساس باید رمزنگاری شود.
- داده‌های هر کاربر/پروژه باید از هم جدا باشند.
- خروج از یک سرویس، فقط Cache و Session همان سرویس را پاک کند؛ مگر حفظ رمزنگاری‌شده با تأیید صریح کاربر تعریف شده باشد. CRM محلی تحت تأثیر قرار نمی‌گیرد.
- CRM باید با قفل Biometric/PIN محافظت شود.
- توکن، محتوای پیام و داده مالی در لاگ ثبت نشوند.

## ۱۸. معیارهای پذیرش MVP

### عمومی

- اپ روی Android و iOS با Expo اجرا می‌شود.
- PWA در حالت آنلاین اجرا می‌شود.
- رابط فارسی و RTL است.
- تم سیستم، روشن و تاریک کار می‌کند.
- تغییر رنگ برند بلافاصله و بعد از restart حفظ می‌شود.
- کنتراست متن و کنترل‌ها در هر تم قابل‌قبول است.
- ناوبری سه‌دکمه‌ای سوپرآپ، پیام‌رسان و مدیریت حساب درست کار می‌کند.
- هر مینی‌اپ محیط و رنگ اختصاصی خودش را دارد.
- عضویت یا ورود سراسری وجود ندارد.
- Auth و Session هر سرویس مستقل است و در MVP Mock می‌ماند.
- CRM بدون Auth هیچ سرویس قابل‌دسترسی است.
- هیچ Project Token Hub در اپ یا PWA وجود ندارد.

### چت

- اپ با Ticket معتبر به Hub متصل می‌شود.
- Ticket منقضی یا نامعتبر رد می‌شود.
- اپ پیام متنی آنلاین می‌فرستد و دریافت می‌کند.
- فایل و ویس در محدوده پشتیبانی‌شده کار می‌کنند.
- پیام تکراری باعث نمایش تکراری نمی‌شود.
- پس از قطع و وصل، Backlog از Planet دریافت می‌شود.
- تاریخچه آفلاین قابل‌مشاهده است.
- در حالت آفلاین ارسال پیام ممکن نیست.
- سطح، اپراتور و وضعیت گفتگو درست نمایش داده می‌شود.
- اگر سطح‌ها جداستند، اپراتور بدون مجوز پیام سطح دیگر را دریافت نمی‌کند.

### فروشگاه و حسابداری

- داده فقط‌خواندنی نمایش داده می‌شود.
- داده آفلاین پس از سینک قبلی قابل‌مشاهده است.
- زمان آخرین به‌روزرسانی نمایش داده می‌شود.
- هیچ عملیات نوشتن در UI وجود ندارد.
- PWA داده فروشگاه و حسابداری را به‌صورت Persistent Cache نگه نمی‌دارد.

### CRM

- CRUD کاملاً محلی انجام می‌شود.
- بدون اینترنت قابل‌استفاده است.
- هیچ درخواست شبکه برای CRM ارسال نمی‌شود.
- قفل Biometric/PIN کار می‌کند.
- Export داده انجام می‌شود.

### سینک

- cursor فقط پس از موفقیت جلو می‌رود.
- خطای شبکه داده محلی را خراب نمی‌کند.
- پیام زنده و Backlog بدون Duplicate یا Gap ادغام می‌شوند.
- حذف سرور در دستگاه اعمال می‌شود.
- خروج از یک سرویس، داده سرویس دیگر یا CRM محلی را افشا نمی‌کند.

## ۲۰. ریسک‌ها و Blockerهای انتشار

| ریسک | وضعیت | اقدام لازم |
|---|---|---|
| Hub فعلی Ticket کوتاه‌عمر را نمی‌پذیرد | Blocker | افزودن احراز هویت Connection Ticket |
| تاریخچه پیام‌های آنلاین در Planet ذخیره نمی‌شود | Blocker | ingest همه پیام‌ها در Planet |
| سطوح پشتیبانی در Hub مجوز جدا ندارند | Blocker در صورت جداسازی داده | Room/Subscription سطح‌بندی‌شده |
| پیام Hub شناسه ماندگار ندارد | Blocker | ایجاد `message_id` canonical در Planet |
| دریافت فایل با Project Token انجام می‌شود | Blocker امنیتی | Proxy فایل از Planet یا Ticket فایل |
| ویس جدید بله نیازمند تبدیل/آپلود است | ریسک رسانه | تعیین دامنه کانال‌های MVP |
| webhook فقط حالت آفلاین را پوشش می‌دهد | ریسک تاریخچه | ingest کامل |
| بازه Retention داده آفلاین مشخص نیست | تصمیم باز | تعیین سیاست cachability |
| خروج مستقل هر سرویس و نگهداری Cache مشخص نیست | تصمیم باز | تعیین سیاست پاک‌سازی per-service |

## ۲۱. سؤال‌های باز

این موارد باید پیش از Freeze شدن مستند فنی یا حداکثر پیش از Release ثبت شوند:

1. اپلیکیشن فقط برای اپراتور است یا مشتری نیز رابط چت دارد؟
2. سطوح پشتیبانی دقیقاً چه هستند و آیا داده‌های هر سطح باید از هم مخفی بمانند؟
3. آیا Ticket با Hub Signature یا Introspection اعتبارسنجی شود؟
4. عمر Ticket و سیاست تازه‌سازی آن چیست؟
5. ارسال ویس روی بله در MVP ضروری است؟
6. پخش ویس و فایل در حالت آفلاین لازم است یا فقط metadata؟
7. داده آفلاین فروشگاه و حسابداری برای چه بازه‌ای نگهداری شود؟
8. هر کاربر به یک فروشگاه دسترسی دارد یا چند فروشگاه؟
9. فرمت Backup/Export CRM چیست؟
10. رنگ قابل‌تنظیم فقط رنگ برند است یا Surfaceها نیز قابل‌شخصی‌سازی هستند؟
11. وضعیت نهایی تحویل پیام در MVP نمایش داده شود یا فقط «ارسال‌شده به سرور»؟
12. مسیر ingest همه پیام‌ها در Planet از قبل وجود دارد یا باید اضافه شود؟
